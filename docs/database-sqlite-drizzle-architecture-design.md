# Database Architecture Design (SQLite and Drizzle)

# Database Location

The database file lives at:

```
%APPDATA%\<app-name>\library.db
```

This resolves to `C:\Users\<user>\AppData\Roaming\<app-name>\library.db` on Windows. Using `AppData\Roaming` means the database survives a full app uninstall and reinstall. The user's library, tags, and play history are never wiped by an update.
The path is constructed at runtime via Electron's `app.getPath('userData')`, never hardcoded.

# Initialization Sequence

The DB is opened once at app start and closed once at app quit. Everything else, including IPC handlers, the file watcher, and the job queue, waits until the DB is ready.

```
app ready
  → open better-sqlite3 connection
  → PRAGMA journal_mode=WAL
  → run Drizzle migrations
  → register IPC handlers
  → start file watcher
```

WAL mode is enabled immediately after the connection opens. It allows reads to proceed concurrently with writes, which matters during background metadata extraction when the job queue is writing while the UI is reading.

# Schema & Migrations

The Drizzle schema is the single source of truth for all table definitions:

```
src/main/db/
  schema.ts          ← all Drizzle table definitions
  migrations/        ← generated migration files, never hand-edited
  index.ts           ← opens the connection, runs migrations, exports db
```

Migrations are generated by `drizzle-kit` and run automatically on every app launch via `migrate()`. If the schema is up to date, this is a no-op. New columns and tables are always added via a new migration and never by editing an existing one.

# Schema Conventions

All primary keys are auto-incrementing integers named `id`. Timestamps are stored as Unix milliseconds (integer, mode: 'timestamp_ms'). Boolean columns use integer mode: 'boolean' (0/1 in SQLite). Foreign key column names mirror their target table plus an "ID" suffix. Cascade deletes propagate from parent to child so orphaned rows never accumulate.

Run `drizzle-kit generate` after any change to a file in `src/backend/database/schema/` to produce a new migration.

# Table Semantics

The play_events table is append only. A row is written when a track finishes or is skipped and it is never updated or deleted afterward.

A play event counts as a skip when the listener stopped before roughly 80% of the track had played. The was_skipped boolean stores that decision.

The queue_source column records where a play started as a short string. The values are "library", "playlist: <id>", "smart: <id>", and "queue".

Smart playlist rules are evaluated in order and each rule's combinator ("and" or "or") joins it to the running result of the rules before it. The first rule's combinator is ignored because it is always the base condition.

A smart playlist rule only sets tag_id when its dimension is "tag_weight". For every other dimension tag_id stays null.

The playback_state table holds a single row whose id is always 1. Every state change rewrites that row so the app can restore playback after a relaunch.

The spotify_imports match_distance column comes from fuse.js, where 0 is a perfect match and 1 is no match at all. Lower means closer.

# Access Rules

There is exactly one `better-sqlite3` connection for the lifetime of the app. It is created in `src/main/db/index.ts` and imported by the repository layer. Nothing else imports it directly.
All database logic lives in `src/main/db/repositories/`. IPC handlers call repository functions. IPC handlers never construct SQL directly.

```
src/main/db/repositories/
  tracks.repo.ts
  tags.repo.ts
  playlists.repo.ts
  playEvents.repo.ts
  analysis.repo.ts
  library.repo.ts
```

The renderer never has access to the DB connection. It gets data by invoking IPC channels, which call repository functions, which return plain serializable objects across the process boundary.
